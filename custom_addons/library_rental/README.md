# Бібліотечний прокат

## Читабельність форми видачі

Неактивні кроки стандартного statusbar Odoo 19 мають штатний колір `text-muted`, що може бути надто світлим у поточній темі. У модулі не було локальних CSS/SCSS-правил, які б його спричиняли. Виправлення обмежене формою `library.loan`: стилі statusbar використовують тематичні Bootstrap-кольори для активного й поверненого станів, а прострочена видача позначається стандартною червоною стрічкою на основі `is_overdue`. Прострочення не є окремим значенням `state`.

SCSS підключений до `web.assets_backend` через manifest. Після оновлення модуля перезавантажте сторінку з очищенням кешу assets (наприклад, додайте `?debug=assets` до URL і виконайте повне оновлення сторінки). Візуальну перевірку світлої/темної теми потрібно виконати у вебінтерфейсі Odoo.

## Автоматичний статус прострочення

Поле `state` зберігає лише `active` або `returned`. Прострочення не змінює стан видачі: активні прострочені видачі залишаються `active`, тому й надалі блокують повторну видачу примірника.

Форма та список показують нестороване обчислюване поле `display_status`: спочатку воно перевіряє фактичне повернення, потім визначає прострочення за `due_date` і поточною датою. Це працює без cron та відображає «Прострочена» одразу. Заповнення `return_date` автоматично встановлює `state = returned`; `fine_amount` обчислюється за фактичною датою. Поле `is_overdue` також лишається динамічним і використовується для червоного виділення рядка списку.

Усі неповернуті видачі мають `state = active` і блокують повторну видачу примірника незалежно від того, чи минув термін. Ця перевірка діє у `onchange`, серверному constraint та механізмі блокування конкурентних записів.

Міграція версії `19.0.1.1.0` повертає наявні записи зі старим `state = overdue` до `active` і видаляє застарілу щоденну cron-дію.

## Українська локалізація

Інтерфейс перекладається каталогом `i18n/uk.po`: він містить переклади назв моделей і полів, статусів, меню, дій, представлень, запланованої дії та повідомлень ORM. Технічні ідентифікатори моделей, полів та XML ID залишаються незмінними. Назва запису видачі формується як «Видача №… — Назва книги».

Щоб увімкнути українську, встановіть мову на базі й імпортуйте каталог перекладу:

```powershell
python odoo-bin i18n loadlang -c odoo.conf -d <назва_бази> -l uk_UA
python odoo-bin i18n import -c odoo.conf -d <назва_бази> -l uk_UA -w custom_addons\library_rental\i18n\uk.po
```

Після цього в Odoo відкрийте **Налаштування → Користувачі**, виберіть українську мову в налаштуваннях кожного користувача та оновіть модуль:

```powershell
python odoo-bin -c odoo.conf -d <назва_бази> -u library_rental --stop-after-init --no-http
```

Каталог `i18n/uk.po` також зчитується Odoo під час оновлення модуля для активованої мови. Завантаження мови та імпорт PO-файлу не змінюють технічні назви моделей, полів або XML ID.

## Обрана структура зв’язків і чому

`library.member` — окрема модель з ім’ям і унікальним номером читацького квитка. Це дає змогу вести читачів незалежно від контактів Odoo, тому модулю не потрібна залежність `contacts`.

`library.book` має зв’язок One2many із примірниками. У `library.copy.book_id`, `library.loan.copy_id` і `library.loan.member_id` використано `ondelete="restrict"`: видалення книги, примірника або читача, на яких посилаються облікові записи, не повинно мовчки знищувати примірники чи історію видач. Унікальність номера читацького квитка забезпечується обмеженням БД. ORM constraint не дозволяє створити більше однієї активної видачі для того самого примірника.

## Відхилення від рекомендованої структури

Відхилень немає. Модуль має `models/`, `views/`, `security/` і `demo/`; каталог `data/` наразі не потрібен.

## Що зроблено без правок

- Додано моделі книг, примірників, читачів і видач.
- Додано доступи, спискові й формові подання, меню та демо-дані.
- Для демо-даних прострочена дата обчислюється від поточної дати під час встановлення.

## Що потребує ручної перевірки

Перевірте обов’язковість полів і правила видалення Many2one:

| Поле | Обов’язкове | `ondelete` | Що перевірити |
|---|---:|---|---|
| `library.copy.book_id` | так | `restrict` | Книгу з примірниками не можна видалити |
| `library.loan.copy_id` | так | `restrict` | Примірник з історією видач не можна видалити |
| `library.loan.member_id` | так | `restrict` | Читача з історією видач не можна видалити |

### Перевірка обчислень і обмежень

Збережені обчислювані поля та їхні повні залежності:

| Поле | `@api.depends` | Ручний сценарій |
|---|---|---|
| `library.loan.due_date` (`store=True`) | `loan_date` | Змініть дату видачі — дата повернення має автоматично зміститися на термін видачі |
| `library.loan.fine_amount` (`store=True`) | `return_date`, `due_date` | Поставте дату фактичного повернення після терміну й перевірте штраф; поставте її у строк і перевірте `0.0`; пошук `search([("fine_amount", ">", 0)])` має знайти цю видачу |

Constraints для перевірки вручну:

| Поля | Сценарій у UI або Odoo shell |
|---|---|
| `copy_id`, `state` | Створіть першу активну видачу примірника, потім спробуйте створити другу активну видачу того самого примірника. Перша має зберегтися, друга — отримати українську помилку валідації. |
| `loan_date`, `due_date` | Для тесту тимчасово задайте `LOAN_PERIOD_DAYS = 0` у `models/loan.py`, оновіть модуль і створіть видачу: constraint має відхилити однакові дати. Поверніть константу до штатного значення після перевірки. |
| `loan_date`, `return_date` | У тестовій видачі задайте `return_date` раніше за `loan_date` і збережіть: система має показати українське повідомлення валідації. |

`is_overdue` не зберігається в БД; у form/list перегляньте активну видачу з минулим терміном та повернену видачу з таким самим минулим терміном.

## Практика ORM у `odoo-bin shell -d <база>`

Замініть `<база>` на назву бази даних. Команди нижче виконуються в Odoo shell; у місцях із `...` підставте реальні ідентифікатори або значення з вашої бази.

### Знайти книги автора через домен

```python
books = env["library.book"].search([("author", "=", "Robert C. Martin")])
books.mapped("name")
```

Очікується список назв книг цього автора, наприклад `["Clean Code"]`, якщо встановлені демо-дані.

### Порахувати вільні примірники книги через домен

```python
book = env["library.book"].search([("name", "=", "Clean Code")], limit=1)
active_copy_ids = env["library.loan"].search([
    ("state", "=", "active"),
]).mapped("copy_id").ids
free_copies = env["library.copy"].search([
    ("book_id", "=", book.id),
    ("id", "not in", active_copy_ids),
])
len(free_copies)
```

Очікується кількість примірників обраної книги, для яких немає активної видачі; у демо для `Clean Code` буде `1`.

### Порахувати вільні примірники циклом по recordset

```python
free_count = 0
for copy in book.copy_ids:
    active_loan = env["library.loan"].search_count([
        ("copy_id", "=", copy.id),
        ("state", "=", "active"),
    ])
    if not active_loan:
        free_count += 1
free_count
```

Очікуваний результат той самий, що й у варіанті з доменом.

### Знайти прострочені активні видачі

```python
from odoo import fields

overdue_loans = env["library.loan"].search([
    ("state", "=", "active"),
    ("due_date", "<", fields.Date.today()),
])
overdue_loans
```

Серед результатів буде принаймні одна демо-видача з простроченим терміном повернення.

### Створити видачу та одразу закрити її

```python
from odoo import fields

loan = env["library.loan"].create({
    "copy_id": ...,  # ID вільного примірника
    "member_id": ...,  # ID читача
})
loan.write({
    "state": "returned",
    "return_date": fields.Date.today(),
})
loan.state, loan.due_date, loan.return_date, loan.fine_amount
```

Термін повернення автоматично встановиться через 14 днів від `loan_date`; після `write()` стан буде `returned`, а штраф — `0.0`, якщо повернення відбулося вчасно.

## Дати, штрафи та перевірки

Тривалість видачі — **14 днів**, ставка штрафу — **5 грн за день**. Обидві константи задані один раз у `models/loan.py` як `LOAN_PERIOD_DAYS` і `FINE_PER_DAY`.

`due_date` обчислюється і зберігається від `loan_date`; `fine_amount` обчислюється і зберігається від `due_date` та `return_date`, тому обидва поля можна фільтрувати й сортувати. `is_overdue` не зберігається: воно потрібне для динамічного виділення прострочених видач у списку, а не для пошуку чи агрегацій; поточна дата береться в контексті користувача.

Додано три `@api.constrains`:

- `copy_id`, `state` — не дозволяє одночасні активні видачі одного примірника.
- `loan_date`, `due_date` — не дозволяє даті повернення бути раніше або в день видачі; це захист на випадок зміни терміну на нульове чи від’ємне значення.
- `loan_date`, `return_date` — не дозволяє вказати фактичне повернення раніше видачі.

Перевірка унікальності активної видачі шукає записи з підвищеними правами, щоб правила доступу не приховали конфлікт. Під час створення та зміни активних видач записи примірників блокуються в стабільному порядку на час транзакції; це серіалізує конкурентні операції для того самого примірника. Constraint лишається обов’язковою перевіркою бізнес-правила. Частковий унікальний індекс не додавався.

Onchange примірника лише показує українське попередження в UI і не блокує збереження. Остаточний захист забезпечує constraint, а блокування рядка примірника закриває гонку між конкурентними транзакціями.

## Практична робота №3 — Бізнес-логіка library_rental

- `due_date` автоматично обчислюється як дата видачі плюс **14 календарних днів**.
- `fine_amount` дорівнює нулю без дати повернення або при поверненні в строк; інакше це кількість днів після терміну, помножена на **5 грн/день**.
- `is_overdue` динамічно позначає активну видачу, у якої термін повернення вже минув.
- Термін і ставка задаються один раз у `models/loan.py`: `LOAN_PERIOD_DAYS` і `FINE_PER_DAY`.
- `due_date` має `@api.depends("loan_date")`, `store=True`; `fine_amount` має `@api.depends("due_date", "return_date")`, `store=True`. Це дозволяє ORM автоматично перераховувати значення та використовувати їх у фільтрах і сортуванні.
- `is_overdue` і `display_status` не зберігаються, бо залежать від поточної дати та потрібні для динамічного UI, а не пошуку чи агрегації.
- Три constraints: унікальність активної видачі примірника запобігає подвійній видачі; перевірка терміну запобігає даті повернення не пізніше дати видачі; перевірка фактичної дати повернення не допускає повернення раніше видачі.
- `@api.onchange("copy_id")` попереджає про зайнятий примірник, але не замінює серверну перевірку й не блокує збереження.

### AI-рев’ю та фактичні правки

Під час перевірки попередньої реалізації знайдено й виправлено:

- зайву залежність `loan_date` у `@api.depends` для `fine_amount` — залишено лише фактичні залежності `due_date` і `return_date`;
- перевірка активної видачі могла не враховувати записи, недоступні через права користувача — пошук constraint та onchange виконується через `sudo()`;
- дві конкурентні транзакції могли одночасно пройти пошук constraint — додано блокування рядків примірників у `create()` і `write()` перед бізнес-перевіркою;
- перевірка прострочення використовувала серверну дату, а не дату з часовим контекстом користувача — використовується `fields.Date.context_today(record)`;
- у кореневому `__init__.py` було двічі імпортовано пакет тестів — залишено один імпорт, умовно ввімкнений лише в режимі тестування;
- змінено текст onchange на задане українське попередження.

Обчислюваний `due_date`, збережений штраф, нестороване прострочення, три окремі constraints та синтаксис `<list>` вже були в початковій реалізації й не потребували виправлення.

### Ручна перевірка в інтерфейсі

1. Відкрийте **Library Rental → Loans** і створіть тестову видачу з датою видачі `01.10.2026`: термін має бути `15.10.2026`.
2. Перевірте повернення `14.10.2026` (штраф `0`), `18.10.2026` (штраф `15`) і `25.10.2026` (штраф `50`).
3. Змініть дату видачі та переконайтеся, що `due_date` і штраф перерахувалися без ручного recompute.
4. Для простроченого активного примірника має з’явитися onchange-попередження, а збереження другої активної видачі має бути відхилене. Перша видача повинна повторно зберігатися без помилкового конфлікту із собою.
5. Вкажіть `return_date` раніше `loan_date`: запис має бути відхилений із повідомленням українською.
6. Звірте, що лише активна видача з терміном до сьогодні має `is_overdue`; повернена або непрострочена — ні.
7. Знайдіть записи через `env["library.loan"].search([("fine_amount", ">", 0)], order="fine_amount desc")`; перевірте, що можна сортувати за штрафом.

### Перевірка майбутніх дат

Для `loan_date` та `return_date` минулі й сьогоднішні дати дозволені, а дата пізніше за поточну дату користувача відхиляється серверними constraints як при створенні, так і при редагуванні через ORM/API. `@api.onchange("loan_date", "return_date")` показує попередження у формі, але не замінює серверну валідацію. Поточна дата визначається через `fields.Date.context_today(record)`.

Обмеження стосується лише фактичних дат видачі й повернення. Майбутній `due_date` дозволений: для видачі сьогодні термін повернення автоматично настає через 14 календарних днів. Перевірте в UI:

1. Створіть видачу з минулою датою, потім зі сьогоднішньою — обидві мають зберегтися.
2. Спробуйте завтра та дату через місяць для `loan_date` — форма має попередити, а сервер має відхилити збереження.
3. Введіть сьогоднішню дату фактичного повернення для вже виданої книги — збереження дозволене; майбутня дата повернення має відхилятися.
4. Для дати видачі сьогодні переконайтеся, що розрахована дата `due_date` через 14 днів лишається дозволеною.
